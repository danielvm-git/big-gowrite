## Purpose
The Functions module is the core serverless compute surface for Appwrite. It allows developers to create, configure, deploy, and execute server-side code functions in any of the supported runtimes (Node.js, Python, PHP, Go, etc.). It manages the full lifecycle: function definition (name, runtime, schedule, timeouts, scopes), code deployments (file upload, VCS/Git-connected, template-based, or duplicate), environment variables, triggered executions (synchronous and asynchronous), and job-service callbacks. It also exposes read-only views of available runtimes, machine specifications, and curated function templates. Background workers handle the asynchronous build pipeline (VCS clone, template merging, artifact upload to the jobs-service), real-time build log streaming (Jobs worker), usage accounting, and site screenshots.

## Workers & Tasks
| Name | Trigger | Purpose |
|------|---------|---------|
| builds | `publisherForBuilds` queue | Handles template-into-VCS deployments: clones user repo + template repo, merges files, commits and pushes to VCS, then hands the build to the jobs-service via `Deployments::createFromUrl()` |
| jobs | `publisherForJobs` queue | Processes jobs-service CloudEvent callbacks (`orchestrator.job.log`, `.artifact`, `.exit`, `.complete`); streams build logs in real-time, applies terminal outcomes (ready/failed), activates deployments, updates schedules, runs VCS git-status actions, dispatches webhooks and function-triggers, tracks build usage |
| screenshots | `publisherForScreenshots` queue | After a successful site deployment, captures light and dark screenshots via a headless browser service (`Client`), saves PNG files to platform storage, updates `deployments` and `sites` documents, and streams log updates via Realtime |

## Key business rules
- 🟢 Function creation is rate-limited: max `_APP_FUNCTIONS_CREATION_ABUSE_LIMIT` (default 50) per project per day.
- 🟢 The runtime must be in the project allow-list (`_APP_FUNCTIONS_RUNTIMES`) if set.
- 🟢 VCS connection requires both `installationId` and `providerBranch` to be provided together with `providerRepositoryId`.
- 🟢 On function creation with VCS, a `repositories` document is created in `dbForPlatform`, and repository-level webhooks are registered with the VCS provider if the installation does not support installation-scoped webhooks.
- 🟢 A `schedules` document is always created in `dbForPlatform` at function creation; it becomes active only when the function has both a non-empty `schedule` CRON and an active deployment.
- 🟢 On VCS disconnect (update with empty `providerRepositoryId`), all associated `repositories` documents are deleted from the platform DB.
- 🟢 Setting a spec (`buildSpecification` or `runtimeSpecification`) that differs from the current one on a function with an active deployment triggers an immediate cold-start via `Executor::deleteRuntime()`.
- 🟢 Creating or updating a variable sets `function.live = false`, forcing a redeploy signal; the schedule is refreshed in the platform DB.
- 🟢 `secret` variables are stored and returned normally via admin/key auth, but their `value` is masked for non-privileged calls.
- 🟢 Code deployments use chunked multipart upload: `content-range` headers drive chunk assembly on the functions storage device; a per-deployment distributed lock (`locks`) serializes concurrent chunk writes.
- 🟢 Synchronous execution (`async=false`) calls `Executor::createExecution()` directly and waits for the result; the execution doc is not persisted to DB in this path, only returned in the response.
- 🟢 Asynchronous execution enqueues a `FunctionMessage` to the functions publisher; scheduled executions create a `schedules` doc in `dbForPlatform` with `SCHEDULE_RESOURCE_TYPE_EXECUTION`.
- 🟢 A short-lived JWT (`_APP_OPENSSL_KEY_V1`, HS256) is generated per execution embedding the project ID + function scopes, and passed as `x-appwrite-key` header to the executor.
- 🟢 Execution log and error output is truncated to `APP_FUNCTION_LOG_LENGTH_LIMIT` and `APP_FUNCTION_ERROR_LENGTH_LIMIT` respectively.
- 🟢 The Jobs worker serializes all callbacks for a single deployment under a per-deployment distributed lock (TTL 30s, timeout 10s) and deduplicates by CloudEvent `id` using a Redis cache (TTL 1h).
- 🟢 Build success requires three callbacks to all arrive: `exit(0)`, `complete`, and for sites the `manifest` artifact — the Jobs worker uses a join pattern in `ready()`.
- 🟢 On a successful build, if `deployment.activate == true`, the function's `deploymentId` is updated and linked routing rules in `dbForPlatform` are repointed.
- 🟡 The `v2` function runtime compatibility layer injects legacy `APPWRITE_FUNCTION_TRIGGER` / `APPWRITE_FUNCTION_DATA` env vars in addition to the v5 headers.
- 🟡 Executions retention pruning is triggered asynchronously via `publisherForDeletes` when `executionsRetentionCount > 0` and `ENABLE_EXECUTIONS_LIMIT_ON_ROUTE` is active.
