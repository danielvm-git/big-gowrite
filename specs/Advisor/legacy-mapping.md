## Purpose
The Advisor module exposes a read-mostly API for surfacing automated analysis results about a project's health, performance, and configuration. It operates on two entities: **Reports** (the top-level result of an analysis run, e.g. a Lighthouse audit or a database-analyzer scan) and **Insights** (actionable findings nested inside a report, each with a severity, type, status, and optional CTA). Clients can list and fetch reports and their nested insights, and can delete reports (which enqueues async deletion of related insights). The module never creates reports or insights directly — those are produced by background workers or external processes writing to the platform database.

## Key business rules
- 🟢 All queries are scoped to the current project via `projectInternalId == project.getSequence()` to prevent cross-project data leakage.
- 🟢 Insights are additionally scoped to their parent report via `reportInternalId == report.getSequence()`.
- 🟢 `getReport` and `deleteReport` skip the `subQueryReportInsights` filter when fetching the report document (to avoid loading all insights for metadata checks), then explicitly re-fetch insights for the response payload.
- 🟢 `listReports` bulk-fetches all insights for the returned report page in a single query (grouped by `reportInternalId`) and distributes them to avoid N+1 queries.
- 🟢 Cursor pagination validates that the cursor document belongs to the current project before use; invalid cursors throw `GENERAL_CURSOR_NOT_FOUND`.
- 🟢 `deleteReport` calls `deleteDocument` synchronously on the `reports` collection, then enqueues a `DeleteMessage` with `DELETE_TYPE_REPORT` for async cleanup of related `insights` documents.
- 🟢 Authentication for all endpoints requires `ADMIN` or `KEY` auth type (no session/JWT); this is a management-level API.
- 🟡 The `total` parameter on list endpoints defaults to `true`; clients can pass `false` to skip the COUNT query for performance.
