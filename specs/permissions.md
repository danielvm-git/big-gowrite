## 1. Tipos de autenticação

| Tipo | Fonte | Comportamento |
|------|-------|---------------|
| **ADMIN** | `APP_AUTH_TYPE_ADMIN` | Acesso privilegiado de plataforma (console/servidor). |
| **KEY** | `APP_AUTH_TYPE_KEY` | API keys de projeto (padrão ou efêmeras JWT HS256). Carregam scopes. |
| **SESSION** | `APP_AUTH_TYPE_SESSION` | Sessão de usuário final (cookies/credenciais). |
| **JWT** | `APP_AUTH_TYPE_JWT` | Token assinado (ex.: JWT por execution de function). |
| **ORGANIZATION** | `APP_AUTH_TYPE_ORGANIZATION` | Escopa o request a um time via header `X-Appwrite-Organization`; **não carrega plataforma própria** — a rota ainda exige um dos tipos acima. |

🟢 Regra: rotas declaram os auth types que as tornam alcançáveis (grupos `api`/`console`/`web`).

## 2. Scopes de API (extraídos dos labels das ações)

Formato `{resource}.{read|write}`; resources: buckets, collections, databases, documents, files, functions, keys, migrations, mocks, platforms, presences, projects, reports, insights, rules, schedules, sites, stages, teams, templates, tokens, users, vcs, webhooks, project, project.oauth2, avatars, devKeys (read/write) + `health.read`.

**Scopes especiais:**
- `account` — operações da própria conta (usuário autenticado).
- `public` — acesso público.
- `home` / `root` — gates de console/plataforma (Init).
- `assistant.read` — proxy do assistente de IA (console).

**Exemplos (mapeamento direto):**
- `users.read`/`users.write` → `/v1/users`
- `teams.read`/`teams.write` → `/v1/teams`
- `functions.read`/`functions.write` → `/v1/functions`
- `buckets.*`/`files.*` → `/v1/storage/buckets` / `/v1/storage/buckets/:bucketId/files`
- `databases.*`/`collections.*`/`documents.*` → `/v1/databases/...`
- `rules.read`/`rules.write` → `/v1/proxy/rules`
- `project.read`/`project.write` → configuração do projeto (`/v1/project`)

## 3. Modelo de permissões de documento (ACL)

Permissões por documento via `Permission::read/update/delete/write` com `Role`:
- `Role::any()` — público.
- `Role::users()` / `Role::guests()` — todos os usuários autenticados / não autenticados.
- `Role::user('{userId}')` — usuário específico.
- `Role::team('{teamId}', '{role}')` — membros do time com a role (ex.: `owner`).
- Permissões de criação default de teams: `Permission::update(Role::team($teamId, 'owner'))`, `Permission::delete(...)` (🟢 visto em Teams/Create.php).

🟢 No storage: `fileSecurity=true` → permissões por arquivo; senão, herda as do bucket.

### 4.2 Papéis de console (🟢 CONFIRMADO — resolvido na revisão)

> ⚠️ **[Revisão]** A versão anterior marcava isto 🟡 ("sem enum fixo no servidor") e citava `view-only`. **Incorreto.** O servidor **define** o enum de papéis e seus scopes explicitamente em `app/config/roles.php`, com os valores em `Appwrite\Utopia\Database\Documents\User` (`User.php:14-21`). **Não existe** papel `view-only`/`analyst`/`billing`/`editor` no código.

Seis papéis, cada um com um conjunto fixo de scopes (`app/config/roles.php`):

| Papel (const) | valor | label | Conjunto de scopes | Notas |
|---------------|-------|-------|--------------------|-------|
| `ROLE_GUESTS` | `guests` | Guests | mínimo (público/sessão) | não autenticado |
| `ROLE_USERS` | `users` | Users | `$member` | usuário final (account, teams, documents, files, executions, presences…) |
| `ROLE_ADMIN` | `admin` | Admin | `$admins` | gestão do projeto (users, databases, functions, keys, webhooks…), **sem** scopes de conta pessoal |
| `ROLE_DEVELOPER` | `developer` | Developer | `$admins` | **conjunto de scopes idêntico a Admin** — diferença é só o label, não é imposta por scope |
| `ROLE_OWNER` | `owner` | Owner | `$member` ∪ `$admins` | superconjunto de tudo; único papel que soma conta pessoal + gestão |
| `ROLE_KEYS` | `keys` | Applications | `global`, `health.read`, `graphql` | API keys de projeto |

**Hierarquia efetiva (por superconjunto de scopes):** `owner` ⊃ `admin` ≡ `developer` ⊃ `users` ⊃ `guests`; `keys` é ortogonal (só API).

- 🟢 `isPrivileged()` = `owner` **OU** `developer` **OU** `admin` (`User.php:104-115`). Esses três são os papéis "privilegiados" do console.
- 🟢 Resolução em runtime: sessão vazia → `guests`; sessão → `users`; API key carrega seu próprio `role`+`scopes` (`app/controllers/shared/api.php:119-140`). Key com role `keys` desliga checagem de autorização para o próprio projeto (`api.php:143-147`).
- 🟡 Nota de código (`api.php:122`, TODO): há intenção futura de derivar scopes da *identity*/token autorizado em vez do config de roles — o modelo atual é o da tabela acima.

## 5. Matriz de acesso por camada

| Camada | Autenticação | Autorização | Notas |
|--------|--------------|-------------|-------|
| API de usuário final | SESSION / JWT / account | scopes + ACL de documento | `/v1/account`, `/v1/teams`... |
| API de projeto | KEY (project) | scopes da key | `/v1/users`, `/v1/functions`... |
| API de console | SESSION do console | `home`/`root` + guards | guard console-project (Init) |
| API de admin | ADMIN | `root` | `/v1/health`, migrações |
| Organização | ORGANIZATION + KEY/ADMIN | time via `X-Appwrite-Organization` | Organization module |
| Web / realtime | SESSION | guards de Init (web) | Webhooks/Console Init |

## 6. Guards e restrições de acesso

- 🟢 **Console-only**: Console module, Notifications, endpoints com guard de console-project.
- 🟢 **Web-only**: Init Web (security headers) em rotas de webhooks.
- 🟢 **Presença**: escrita de `userId` restrita a key/privilegiados.
- 🟢 **Webhooks**: projeto console bloqueado.
- 🟢 **Tokens de recurso**: criação exige permissão UPDATE no bucket/file; ADMIN/KEY apenas.
- 🟢 **Scoping multi-tenant**: `projectInternalId` em todas as consultas de dados (anti-vazamento).
- 🟢 **MembershipsPrivacy**: controle de exposição de campos da membership.
- 🟢 **Rate limits por ação** (🟢 CONFIRMADO — resolvido na revisão; ver §8).
