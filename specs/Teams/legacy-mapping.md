## Purpose
The Teams module provides collaboration primitives for Appwrite projects. It manages teams (groups of users with a shared identity and role set), team memberships (the link between a user and a team with assigned roles), team preferences (arbitrary JSON stored on the team), and the invitation/confirmation flow that lets new users be added to a team via email, SMS, or direct userId lookup. Teams exist in the per-project database and are the primary access-control grouping mechanism used across Appwrite resources.

## Key business rules
- 🟢 On team creation in user (non-app, non-privileged) mode, the creating user is automatically added as an owner membership with `confirm=true`. App/server mode skips this — team `total` starts at 0.
- 🟢 Creating a membership in app/privileged mode adds the user directly (confirmed, `joined` set immediately) and increments `total`. User mode creates an unconfirmed membership and sends an email or SMS invite.
- 🟢 Only the team owner, a privileged user, or an app key may send invitations.
- 🟢 SMTP must be configured (`_APP_SMTP_HOST`) when an email invite is sent by a non-privileged/non-app actor.
- 🟢 SMS invite requires `_APP_SMS_PROVIDER` to be configured.
- 🟢 `createTeamMembership` accepts `userId`, `email`, or `phone` (at least one required). When `userId` is provided alongside email/phone, they must match the stored values.
- 🟢 If no existing user matches email/phone at invite time, a new stub user is created with a random password hash and `passwordUpdate=null`.
- 🟢 Email validation rules (disposable, canonical, free, corporate) are enforced on new user creation during invite, gated by project `auths` settings and plan features.
- 🟢 Membership status confirmation (`updateTeamMembershipStatus`) validates the invite secret via `proofForToken`; throws `TEAM_INVALID_SECRET` on mismatch.
- 🟢 If the invitee is not already logged in when confirming, a new session is created and set as a cookie (with fallback header for cross-domain).
- 🟢 The `membershipsPrivacy` settings (`membershipsUserName`, `membershipsUserEmail`, `membershipsUserId`, `membershipsUserPhone`, `membershipsMfa`) control which user fields are exposed in membership list/get responses; privileged users and app keys always see all fields.
- 🟢 In the console project, deleting a team or removing an owner is blocked if they are the last owner (`MEMBERSHIP_DELETION_PROHIBITED` / `MEMBERSHIP_DOWNGRADE_PROHIBITED`).
- 🟢 When the primary team user (the one stored as `team.userId`) is removed, the next confirmed member is promoted to primary.
- 🟢 Deleting a team: memberships are deleted synchronously; team-owned projects are deleted asynchronously (publisher message `DELETE_TYPE_TEAM_PROJECTS`) only when on the console project.
- 🟡 The `total` counter on teams tracks only confirmed members; decrement occurs on confirmed-member removal.
