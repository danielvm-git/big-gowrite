## Stories

### US-USR-01 — Create a user, including imported password hashes
**As a** server-side administrator,
**I want** to provision users directly (plaintext or legacy hash import),
**so that** users can exist before/without self-registration.
**Priority:** Must · **Unit:** Users (RF-01, RF-02) · **Confidence:** 🟢
**HTTP:** `POST /v1/users` → `createUser` · `POST /v1/users/{argon2|bcrypt|md5|phpass|scrypt|scrypt-modified|sha}` → `create*User`

**Acceptance criteria**
- Given a valid payload, When I create a plaintext user, Then the user is stored with a hashed password and returned. (🟢)
- Given a supported hash variant, When I import a user with an existing hash + salt, Then the hash is adopted verbatim (no re-hash). (🟢)
- Given an unsupported/unknown variant, When I import, Then an invalid-parameter error is returned. (🟢)

### US-USR-02 — Search, inspect and delete users
**As a** administrator,
**I want** to list/get/delete users,
**so that** I can manage the user directory.
**Priority:** Must · **Unit:** Users (RF-03) · **Confidence:** 🟢
**HTTP:** `GET /v1/users` → `listUsers` · `GET /v1/users/{userId}` → `getUser` · `DELETE /v1/users/{userId}` → `deleteUser`

**Acceptance criteria**
- Given a query, When I list users, Then pagination and search filters apply. (🟢)
- Given an existing user, When I get them by id, Then the full profile is returned. (🟢)
- Given a deleted user, When I try to get them, Then `USER_NOT_FOUND` is returned. (🟢)

### US-USR-03 — Update a user's profile attributes
**As a** administrator,
**I want** to change name/email/phone/password/status/labels/prefs/verification,
**so that** I can correct or govern accounts without the user's session.
**Priority:** Must · **Unit:** Users (RF-04) · **Confidence:** 🟢
**HTTP:** `PATCH /v1/users/{userId}/{name|email|phone|password|status|prefs}` → `updateUser*` · `PUT /v1/users/{userId}/labels` → `updateUserLabels`

**Acceptance criteria**
- Given a user, When I update email, Then the change is persisted (with conflict checks). (🟢)
- Given a user, When I update status, Then blocking/unblocking takes effect immediately. (🟢)
- Given a user, When I update labels, Then the label set is replaced (not merged). (🟢)

### US-USR-04 — Manage a user's sessions
**As a** administrator,
**I want** to create/list/delete sessions for a user,
**so that** I can act on their behalf or revoke access.
**Priority:** Must · **Unit:** Users (RF-05) · **Confidence:** 🟢
**HTTP:** `POST /v1/users/{userId}/sessions` → `createUserSession` · `GET /v1/users/{userId}/sessions` → `listUserSessions` · `DELETE /v1/users/{userId}/sessions` → `deleteUserSessions` · `DELETE /v1/users/{userId}/sessions/{sessionId}` → `deleteUserSession`

**Acceptance criteria**
- Given a user, When I create a session, Then a session document is created for them. (🟢)
- Given active sessions, When I delete all sessions, Then all sessions are revoked. (🟢)
- Given an admin acting for a user (impersonation), When I create a session, Then it is marked as impersonated. (🟡)

### US-USR-05 — Manage message targets for a user
**As a** administrator,
**I want** to create/list/get/update/delete targets (email, phone, push),
**so that** messaging providers can reach the user.
**Priority:** Must · **Unit:** Users (RF-06) · **Confidence:** 🟢
**HTTP:** `POST /v1/users/{userId}/targets` → `createUserTarget` · `GET /v1/users/{userId}/targets` → `listUserTargets` · `GET/PATCH/DELETE /v1/users/{userId}/targets/{targetId}` → `getUserTarget` / `updateUserTarget` / `deleteUserTarget`

**Acceptance criteria**
- Given a user, When I create a target, Then it is linked to the user and provider. (🟢)
- Given a target, When I update it, Then provider identifier changes are persisted. (🟢)
- Given a stale target, When I delete it, Then it no longer appears in the list. (🟢)

### US-USR-06 — Issue JWTs and list memberships/identities
**As a** administrator,
**I want** to mint short-lived JWTs and inspect memberships/identities,
**so that** I can grant scoped access and audit the user's links.
**Priority:** Should · **Unit:** Users (RF-07, RF-08) · **Confidence:** 🟢
**HTTP:** `POST /v1/users/{userId}/jwts` → `createUserJWT` · `GET /v1/users/{userId}/memberships` → `listUserMemberships` · `GET /v1/users/{userId}/identities` → `listUserIdentities` · `DELETE /v1/users/{userId}/identities/{identityId}` → `deleteUserIdentity`

**Acceptance criteria**
- Given a user, When I create a JWT, Then a short-lived signed token is returned. (🟢)
- Given OAuth-linked identities, When I list them, Then provider and uid are exposed. (🟢)
- Given an identity, When I delete it, Then the OAuth linkage is removed. (🟢)

### US-USR-07 — Manage MFA for a user
**As a** administrator,
**I want** to view/reset a user's MFA state (factors, recovery codes),
**so that** I can support users locked out of MFA.
**Priority:** Should · **Unit:** Users (RF-09) · **Confidence:** 🟢
**HTTP:** `PATCH /v1/users/{userId}/mfa` → `updateUserMFA` · `GET /v1/users/{userId}/mfa/factors` → `listUserMFAFactors` · `GET/POST/PUT /v1/users/{userId}/mfa/recovery-codes` → `*UserMFARecoveryCodes` · `DELETE /v1/users/{userId}/mfa/authenticators/{type}` → `deleteUserMFAAuthenticator`

**Acceptance criteria**
- Given a user, When I list factors, Then the same factor model as Account is returned. (🟢)
- Given a locked-out user, When I regenerate recovery codes, Then a fresh set replaces the old one. (🟢)
