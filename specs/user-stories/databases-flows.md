# User Stories: Databases (collections, tables, transactions, vectors)

> Generated by the **Reversa Writer** (Fase 4 — `user-stories/`).
> Sources: `specs/Databases/requirements.md`, `design.md`, `legacy-mapping.md`, `specs/openapi/appwrite.yaml`.
> Confidence: 🟢 CONFIRMED (code) · 🟡 INFERRED · 🔴 GAP
> The legacy mapping documents four namespaces — `/v1/databases` (collections+documents), `/v1/tablesdb` (tables+rows+columns), `/v1/documentsdb` (tables+rows, no columns) and `/v1/vectorsdb` (collections+documents + similarity query). Stories below use the legacy namespace; the mirrored namespaces expose the same behavior with their own paths.

## Stories

### US-DB-01 — Create and manage databases (all four types)
**As a** developer,
**I want** to create, list, update and delete databases,
**so that** I can organize structured data per project.
**Priority:** Must · **Unit:** Databases (RF-01) · **Confidence:** 🟢
**HTTP:** `POST /v1/databases` → `createDatabase` · `GET /v1/databases` → `listDatabases` · `GET/PUT/DELETE /v1/databases/{databaseId}` → `getDatabase` / `updateDatabase` / `deleteDatabase`

**Acceptance criteria**
- Given a name, When I create a database, Then it is persisted and returned. (🟢)
- Given a database, When I delete it, Then deletion is asynchronous with cleanup of children. (🟢)
- Given the same structure, When I use tablesdb/documentsdb/vectorsdb, Then the same CRUD semantics apply under their paths. (🟡)

### US-DB-02 — Manage collections (tables) with inline attributes and indexes
**As a** developer,
**I want** to create collections (optionally with attributes and indexes inline),
**so that** schemas are defined in one call.
**Priority:** Must · **Unit:** Databases (RF-02) · **Confidence:** 🟢
**HTTP:** `POST /v1/databases/{databaseId}/collections` → `createCollection` · `GET /v1/databases/{databaseId}/collections` → `listCollections` · `GET/PATCH/DELETE /v1/databases/{databaseId}/collections/{collectionId}` → `getCollection` / `updateCollection` / `deleteCollection`

**Acceptance criteria**
- Given a name, When I create a collection, Then it is created with default permissions. (🟢)
- Given inline attribute/index definitions, When I create a collection, Then they are applied in the same request. (🟢)
- Given a deleted collection, When its documents are queried, Then they are no longer accessible. (🟢)

### US-DB-03 — CRUD documents (rows), single and bulk
**As a** developer,
**I want** to create, read, update, upsert and delete documents individually or in bulk,
**so that** application data can be managed efficiently.
**Priority:** Must · **Unit:** Databases (RF-03) · **Confidence:** 🟢
**HTTP:** `POST/PATCH/PUT/DELETE /v1/databases/{databaseId}/collections/{collectionId}/documents[/{documentId}]` → `createDocument` / `updateDocument` / `upsertDocument` / `deleteDocument` (+ bulk `updateDocuments`, `upsertDocuments`, `deleteDocuments`)

**Acceptance criteria**
- Given a valid document, When I create it, Then it is stored with `$id` and timestamps. (🟢)
- Given a bulk payload (array of documents), When I create, Then all are created atomically per batch semantics. (🟢)
- Given optimistic-lock expectations, When a concurrent update conflicts, Then the write is rejected. (🟡)
- Given an increment/decrement call on a numeric attribute, When the target matches a query, Then the value changes accordingly. (🟢)

### US-DB-04 — Define typed attributes (16 types) asynchronously
**As a** developer,
**I want** to add typed attributes (string, integer, bigint, float, boolean, datetime, email, ip, enum, varchar, text, mediumtext, longtext, url, point, line, polygon, relationship),
**so that** the schema enforces types and query performance.
**Priority:** Must · **Unit:** Databases (RF-04) · **Confidence:** 🟢
**HTTP:** `POST /v1/databases/{databaseId}/collections/{collectionId}/attributes/{type}` → `create*Attribute` · `GET /v1/databases/{databaseId}/collections/{collectionId}/attributes` → `listAttributes` · `PATCH/DELETE .../attributes/{attributeId}` → `update*Attribute` / `deleteAttribute`

**Acceptance criteria**
- Given a typed attribute payload, When I create it, Then the attribute is queued and eventually available (202 Accepted). (🟢)
- Given an existing attribute, When I update defaults/required, Then the change is applied. (🟢)
- Given an attribute in use, When I delete it, Then removal is asynchronous. (🟢)

### US-DB-05 — Build and maintain indexes
**As a** developer,
**I want** to create, list, get and delete indexes,
**so that** queries on collections stay fast.
**Priority:** Must · **Unit:** Databases (RF-05) · **Confidence:** 🟢
**HTTP:** `POST /v1/databases/{databaseId}/collections/{collectionId}/indexes` → `createIndex` · `GET .../indexes` → `listIndexes` · `GET/DELETE .../indexes/{indexId}` → `getIndex` / `deleteIndex`

**Acceptance criteria**
- Given an index definition, When I create it, Then it is built asynchronously (202 Accepted). (🟢)
- Given an index, When I list/get it, Then its state (building/available/failed) is visible. (🟢)
- Given a stale index, When I delete it, Then it stops being used by the query planner. (🟢)

### US-DB-06 — Run transactions
**As a** developer,
**I want** to open, stage operations, commit and roll back transactions,
**so that** multi-document writes are atomic.
**Priority:** Must · **Unit:** Databases (RF-06) · **Confidence:** 🟢
**HTTP:** `POST /v1/databases/transactions` → `createDatabasesTransaction` · `GET /v1/databases/transactions` → `listDatabasesTransactions` · `GET/PATCH/DELETE /v1/databases/transactions/{transactionId}` → `getDatabasesTransaction` / `updateDatabasesTransaction` (commit/rollback) / `deleteDatabasesTransaction` · `POST /v1/databases/transactions/{transactionId}/operations` → `createDatabasesTransactionOperations`

**Acceptance criteria**
- Given a session, When I open a transaction, Then a TTL-bounded token is returned. (🟢)
- Given a staged batch, When I commit, Then the writes become visible atomically. (🟢)
- Given a pending transaction, When I roll back, Then staged operations are discarded. (🟢)

### US-DB-07 — Vector similarity search and embeddings
**As a** developer,
**I want** to query documents by vector similarity and generate embeddings,
**so that** semantic search works over stored vectors.
**Priority:** Should · **Unit:** Databases (RF-07, RF-08) · **Confidence:** 🟢
**HTTP:** `POST /v1/vectorsdb/{databaseId}/collections/{collectionId}/documents/query` → `createVectorsDBDocumentsQuery` · `POST /v1/embeddings/text` → `createTextEmbedding`

**Acceptance criteria**
- Given a query vector, When I search, Then ranked results are returned (with optional TTL cache). (🟢)
- Given a text, When I request embeddings, Then the generated vectors are returned. (🟢)
