## Stories

### US-PRJ-01 — Get/delete the current project and manage labels
**As a** console user,
**I want** to view or delete the current project and set labels,
**so that** I control the project lifecycle and tagging.
**Priority:** Must · **Unit:** Project (RF-01, RF-02) · **Confidence:** 🟢
**HTTP:** `GET /v1/project` → `getProject` · `DELETE /v1/project` → `deleteProject` · `PUT /v1/project/labels` → `updateProjectLabels`

**Acceptance criteria**
- Given a project context, When I get the project, Then its metadata is returned. (🟢)
- Given a project, When I delete it, Then it is removed with async cleanup. (🟢)
- Given a label set, When I replace labels, Then the previous set is fully replaced. (🟢)

### US-PRJ-02 — Configure SMTP and email templates
**As a** console user,
**I want** to set SMTP settings, send test emails and customize templates,
**so that** transactional emails are branded and reliable.
**Priority:** Must · **Unit:** Project (RF-04, RF-05) · **Confidence:** 🟢
**HTTP:** `PATCH /v1/project/smtp` → `updateProjectSMTP` · `POST /v1/project/smtp/tests` → `createProjectSMTPTest` · `GET /v1/project/templates/email` → `listProjectEmailTemplates` · `GET/PATCH /v1/project/templates/email/{templateId}` → `getProjectEmailTemplate` / `updateProjectEmailTemplate`

**Acceptance criteria**
- Given SMTP settings, When I update, Then they are persisted and used for mail. (🟢)
- Given a test request, When SMTP is configured, Then a test email is delivered. (🟢)
- Given a template id, When I update it, Then the customized template replaces the default. (🟢)

### US-PRJ-03 — Manage project variables
**As a** console user,
**I want** to create/list/get/update/delete project variables,
**so that** shared configuration is centralized.
**Priority:** Must · **Unit:** Project (RF-06) · **Confidence:** 🟢
**HTTP:** `POST /v1/project/variables` → `createProjectVariable` · `GET /v1/project/variables` → `listProjectVariables` · `GET/PUT/DELETE /v1/project/variables/{variableId}` → `getProjectVariable` / `updateProjectVariable` / `deleteProjectVariable`

**Acceptance criteria**
- Given a key/value, When I create a variable, Then it is stored (values masked on read). (🟢)
- Given a variable, When I update it, Then the value is replaced. (🟢)
- Given a variable, When I delete it, Then it is removed from resolution. (🟢)

### US-PRJ-04 — Manage API keys (including ephemeral)
**As a** console user,
**I want** to create/list/get/update/delete API keys,
**so that** server-side access is scoped and revocable.
**Priority:** Must · **Unit:** Project (RF-07) · **Confidence:** 🟢

### US-PRJ-05 — Manage platforms (5 types)
**As a** console user,
**I want** to add/update/remove platforms (web, android, apple, windows, linux),
**so that** client SDKs authenticate correctly.
**Priority:** Must · **Unit:** Project (RF-08) · **Confidence:** 🟢
**HTTP:** `POST /v1/project/platforms/{type}` → `createProject*Platform` · `GET /v1/project/platforms` → `listProjectPlatforms` · `GET/PATCH/DELETE /v1/project/platforms/{platformId}` → `getProjectPlatform` / `updateProjectPlatform` / `deleteProjectPlatform`

**Acceptance criteria**
- Given a platform type, When I create it, Then its key/credentials are stored. (🟢)
- Given a platform, When I update it, Then name/credentials are replaced. (🟢)
- Given a platform, When I delete it, Then SDK auth for that platform is revoked. (🟢)

### US-PRJ-06 — Apply security policies
**As a** console user,
**I want** to list, get and update the 12 project policies (password, sessions, user limits…),
**so that** security baselines are enforced.
**Priority:** Must · **Unit:** Project (RF-10) · **Confidence:** 🟢
**HTTP:** `GET /v1/project/policies` → `listPolicies` · `GET /v1/project/policies/{policyId}` → `getProjectPolicy` · `PATCH /v1/project/policies/{policy}` → `updateProject*Policy`

**Acceptance criteria**
- Given a project, When I list policies, Then all policies with current values are returned. (🟢)
- Given a policy id, When I update it, Then the new value is validated and persisted. (🟢)
- Given an invalid value, When I update, Then the change is rejected. (🟢)

### US-PRJ-07 — Configure OAuth2 providers (38) and protocol/service toggles
**As a** console user,
**I want** to list/get/update OAuth2 providers and toggle protocols/services/auth-methods,
**so that** sign-in options are controlled.
**Priority:** Must · **Unit:** Project (RF-03, RF-11) · **Confidence:** 🟢
**HTTP:** `GET /v1/project/oauth2` → `listProjectOAuth2` · `GET/PATCH /v1/project/oauth2/{provider}` → `getProjectOAuth2` / `updateProjectOAuth2Provider` · `PATCH /v1/project/protocols/{protocolId}` → `updateProjectProtocol` · `PATCH /v1/project/services/{serviceId}` → `updateProjectService` · `PATCH /v1/project/auth-methods/{methodId}` → `updateProjectAuthMethod`

**Acceptance criteria**
- Given a provider, When I update client id/secret, Then the provider is enabled for OAuth sessions. (🟢)
- Given a service toggle, When I disable it, Then its endpoints become unavailable. (🟢)
- Given an auth method toggle, When I disable it, Then that sign-in method is blocked. (🟢)

### US-PJS-01 — Provision and onboard projects
**As a** console user,
**I want** to create a project (provisioning its database), transfer teams and track onboarding,
**so that** new projects start correctly.
**Priority:** Must · **Unit:** Projects (RF-01, RF-02, RF-04, RF-07) · **Confidence:** 🟢
**HTTP:** `POST /v1/projects` → `createProject` · `GET /v1/projects` → `listProjects` · `PATCH /v1/projects/{projectId}` → `updateProject` · `PATCH /v1/projects/{projectId}/team` → `updateProjectTeam` · `PATCH /v1/projects/{projectId}/onboarding-stages` → `updateOnboardingStages`

**Acceptance criteria**
- Given a valid plan/team, When I create a project, Then its database is provisioned. (🟢)
- Given a project, When I transfer it, Then the team association changes. (🟢)
- Given a stage, When I update onboarding, Then the console wizard progresses. (🟢)

### US-CNS-01 — Console bootstrap data
**As a** console client,
**I want** to fetch config variables, scopes, OAuth2 providers, templates and resources,
**so that** the console renders correctly per project/organization.
**Priority:** Should · **Unit:** Console (RF-01..RF-07) · **Confidence:** 🟢
**HTTP:** `GET /v1/console/variables` → `getVariables` · `GET /v1/console/scopes/project` → `listConsoleProjectScopes` · `GET /v1/console/scopes/organization` → `listConsoleOrganizationScopes` · `GET /v1/console/oauth2-providers` → `listOAuth2Providers` · `GET /v1/console/templates/email/{templateId}` → `getConsoleEmailTemplate` · `GET /v1/console/resources` → `getResource` · `POST /v1/console/assistant` → `createAssistantQuery`

**Acceptance criteria**
- Given a session, When I request scopes, Then the allowed scopes for the role are returned. (🟢)
- Given a template id, When I request it, Then the default email template is rendered. (🟢)
- Given a domain, When I check availability, Then availability is reported. (🟢)
- Given a prompt, When I query the assistant, Then the response streams (SSE). (🟢)

**HTTP:** `POST /v1/project/keys` → `createProjectKey` · `GET /v1/project/keys` → `listProjectKeys` · `GET/PUT/DELETE /v1/project/keys/{keyId}` → `getProjectKey` / `updateProjectKey` / `deleteProjectKey` · `POST /v1/project/keys/ephemeral` → `createEphemeralProjectKey`

**Acceptance criteria**
- Given scopes, When I create a key, Then the secret is returned once. (🟢)
- Given a key, When I update scopes/expiry, Then access changes immediately. (🟢)
- Given an ephemeral key, When created, Then it carries a short TTL. (🟡)
