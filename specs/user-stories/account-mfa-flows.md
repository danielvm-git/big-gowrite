## Stories

### US-ACC-01 — Enable or disable MFA on my account
**As a** user of an Appwrite-backed app,
**I want** to turn MFA on or off for my own account,
**so that** I can raise or lower the authentication bar for sensitive operations.
**Priority:** Must · **Unit:** Account (RF-01) · **Confidence:** 🟢
**HTTP:** `PATCH /v1/account/mfa` → `updateMFA`

**Acceptance criteria**
- Given a confirmed session, When I enable MFA, Then the account `mfa` flag is persisted and returned in the profile. (🟢)
- Given MFA enabled, When I disable it, Then subsequent challenges are no longer required. (🟢)
- Given a missing/invalid session, When I call the endpoint, Then an auth error is returned (no state change). (🟢)

### US-ACC-02 — Register a TOTP authenticator
**As a** user,
**I want** to add an authenticator app (TOTP),
**so that** I can generate time-based codes for MFA.
**Priority:** Must · **Unit:** Account (RF-03, RF-04) · **Confidence:** 🟢
**HTTP:** `POST /v1/account/mfa/authenticators/{type}` → `createMFAAuthenticator` · `PUT /v1/account/mfa/authenticators/{type}` → `updateMFAAuthenticator`

**Acceptance criteria**
- Given a session, When I create a TOTP authenticator, Then a secret + provisioning URI are returned for the QR code. (🟢)
- Given a generated secret, When I confirm with a live OTP, Then the authenticator becomes verified. (🟢)
- Given a wrong OTP, When I confirm, Then verification fails and the authenticator stays unverified. (🟡)

### US-ACC-03 — Complete an MFA challenge during sign-in
**As a** user,
**I want** to answer a challenge (email, phone, TOTP or recovery code),
**so that** my session is elevated to MFA-verified only after proof.
**Priority:** Must · **Unit:** Account (RF-06, RF-07) · **Confidence:** 🟢
**HTTP:** `POST /v1/account/mfa/challenges` → `createMFAChallenge` · `PUT /v1/account/mfa/challenges` → `updateMFAChallenge`

**Acceptance criteria**
- Given MFA enabled, When I initiate a challenge, Then a challenge token is returned and the delivery method is invoked. (🟢)
- Given a pending challenge, When I submit the correct code, Then the session factors are elevated (MFA satisfied). (🟢)
- Given a wrong/expired code, When I complete the challenge, Then it fails and factors are not elevated. (🟢)

### US-ACC-04 — Manage backup recovery codes
**As a** user,
**I want** to generate and rotate recovery codes,
**so that** I can regain access if I lose my authenticator.
**Priority:** Must · **Unit:** Account (RF-08, RF-09, RF-10) · **Confidence:** 🟢
**HTTP:** `POST /v1/account/mfa/recovery-codes` → `createMFARecoveryCodes` · `GET /v1/account/mfa/recovery-codes` → `getMFARecoveryCodes` · `PATCH /v1/account/mfa/recovery-codes` → `updateMFARecoveryCodes`

**Acceptance criteria**
- Given MFA enabled and no codes yet, When I request recovery codes, Then a fresh set is generated and shown once. (🟢)
- Given an existing set, When I list codes, Then the stored (hashed) codes are returned. (🟢)
- Given a compromised set, When I regenerate, Then the previous set is invalidated. (🟢)

### US-ACC-05 — Inspect available MFA factors
**As a** user,
**I want** to list which factors are available and which are already verified,
**so that** I know which challenges I can use.
**Priority:** Should · **Unit:** Account (RF-02) · **Confidence:** 🟢
**HTTP:** `GET /v1/account/mfa/factors` → `listMFAFactors`

**Acceptance criteria**
- Given a session, When I list factors, Then each factor (email, phone, totp, recovery_code) shows available/verified state. (🟢)
- Given a session, When I remove an authenticator, Then the factor list reflects the change. (🟢)
