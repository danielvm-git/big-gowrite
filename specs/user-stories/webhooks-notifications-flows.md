## Stories

### US-WHK-01 — Create and list webhooks
**As a** developer,
**I want** to register webhooks for project events,
**so that** external services are notified of Appwrite activity.
**Priority:** Must · **Unit:** Webhooks (RF-01, RF-02) · **Confidence:** 🟢
**HTTP:** `POST /v1/webhooks` → `createWebhook` · `GET /v1/webhooks` → `listWebhooks`

**Acceptance criteria**
- Given event names + a URL, When I create a webhook, Then a signature key is generated and returned once. (🟢)
- Given a project, When I list webhooks, Then only that project's webhooks are returned. (🟢)
- Given a disabled/enabled flag, When I create, Then delivery behavior honors the state. (🟢)

### US-WHK-02 — Get, update and rotate webhook secrets
**As a** developer,
**I want** to read, replace and rotate webhooks,
**so that** configuration stays correct and secrets stay fresh.
**Priority:** Must · **Unit:** Webhooks (RF-03, RF-04, RF-06) · **Confidence:** 🟢
**HTTP:** `GET /v1/webhooks/{webhookId}` → `getWebhook` · `PUT /v1/webhooks/{webhookId}` → `updateWebhook` · `PATCH /v1/webhooks/{webhookId}/secret` → `updateWebhookSecret` · `DELETE /v1/webhooks/{webhookId}` → `deleteWebhook`

**Acceptance criteria**
- Given a webhook, When I get it, Then its config is returned (secret masked). (🟢)
- Given new config, When I update, Then the webhook is replaced. (🟢)
- Given a suspected leak, When I rotate the secret, Then a new signature key is issued. (🟢)
- Given a webhook, When I delete it, Then no further deliveries are attempted. (🟢)

### US-WHK-03 — Signed event delivery
**As a** developer,
**I want** payloads signed with the webhook signature key,
**so that** I can verify deliveries originate from Appwrite.
**Priority:** Should · **Unit:** Webhooks (RF-05, delivery) · **Confidence:** 🟡
**HTTP:** (delivery side — worker `webhooks`; signature header on each POST)

**Acceptance criteria**
- Given a triggered event, When the webhook worker delivers, Then the payload is POSTed with the signature header. (🟡)
- Given a failed delivery, When retries are exhausted, Then the failure is recorded. (🟡)

### US-NTF-01 — Read and acknowledge console notifications
**As a** console user,
**I want** to list notifications and mark them read,
**so that** I stay informed of platform news without noise.
**Priority:** Should · **Unit:** Notifications (RF-01, RF-02) · **Confidence:** 🟢
**HTTP:** `GET /v1/notifications` → `listNotifications` · `PATCH /v1/notifications/{notificationId}` → `updateNotification`

**Acceptance criteria**
- Given a session, When I list notifications, Then the catalog is returned with read state. (🟢)
- Given a notification, When I update it, Then the read flag is persisted. (🟢)
- Given a public asset, When I request the logo, Then the image is served without auth. (🟢)

### US-PRS-01 — Track and list online presences
**As a** developer,
**I want** to upsert, update, list, get and delete presence records,
**so that** realtime applications know who is online.
**Priority:** Should · **Unit:** Presences (RF-01..RF-05) · **Confidence:** 🟢
**HTTP:** `PUT /v1/presences/{presenceId}` → `upsertPresence` · `PATCH /v1/presences/{presenceId}` → `updatePresence` · `GET /v1/presences` → `listPresences` · `GET/DELETE /v1/presences/{presenceId}` → `getPresence` / `deletePresence`

**Acceptance criteria**
- Given a presence id, When I upsert, Then the record is created or updated with the new payload. (🟢)
- Given an active user, When I list presences, Then results are served from the TTL cache. (🟢)
- Given a disconnected user, When the TTL expires, Then the presence is no longer listed. (🟢)
