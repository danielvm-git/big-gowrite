## Stories

### US-TMS-01 — Create and manage a team
**As a** user,
**I want** to create, rename and delete teams,
**so that** I can group users under a shared access-control unit.
**Priority:** Must · **Unit:** Teams (RF-01) · **Confidence:** 🟢
**HTTP:** `POST /v1/teams` → `createTeam` · `GET /v1/teams/{teamId}` → `getTeam` · `PUT /v1/teams/{teamId}` → `updateTeamName` · `DELETE /v1/teams/{teamId}` → `deleteTeam`

**Acceptance criteria**
- Given a user-mode session, When I create a team, Then I am auto-added as confirmed owner and `total` reflects it. (🟢)
- Given app/server mode, When I create a team, Then no creator membership is created. (🟢)
- Given a console team with members, When I delete it, Then memberships are sync-deleted and team-owned projects are async-deleted. (🟢)

### US-TMS-02 — Invite or directly add members
**As a** team owner (or privileged caller),
**I want** to add members by userId, email or phone,
**so that** the right people join the team.
**Priority:** Must · **Unit:** Teams (RF-03) · **Confidence:** 🟢
**HTTP:** `POST /v1/teams/{teamId}/memberships` → `createTeamMembership`

**Acceptance criteria**
- Given a privileged/app key, When I add by userId, Then the membership is created confirmed and `total` increments. (🟢)
- Given a user session, When I invite by email/phone, Then an unconfirmed membership is created and an invite (email/SMS) is sent. (🟢)
- Given no matching user for an email invite, When SMTP is configured, Then a stub user is created with a random password hash and the invite is sent. (🟢)
- Given SMTP not configured, When a non-privileged email invite is attempted, Then it fails with a configuration error. (🟢)

### US-TMS-03 — Confirm a membership invite
**As a** invited user,
**I want** to confirm my membership with the invite secret,
**so that** I actually join the team.
**Priority:** Must · **Unit:** Teams (RF-07) · **Confidence:** 🟢
**HTTP:** `PATCH /v1/teams/{teamId}/memberships/{membershipId}/status` → `updateTeamMembershipStatus`

**Acceptance criteria**
- Given a valid invite secret, When I confirm, Then the membership is marked confirmed and `total` increments. (🟢)
- Given an invalid/expired secret, When I confirm, Then `TEAM_INVALID_SECRET` is returned. (🟢)
- Given a not-logged-in invitee, When I confirm, Then a session cookie is set for the new user (fallback header for cross-domain). (🟢)

### US-TMS-04 — Manage roles and remove members safely
**As a** team owner,
**I want** to update member roles and remove members,
**so that** the team's access control stays correct.
**Priority:** Must · **Unit:** Teams (RF-05, RF-06) · **Confidence:** 🟢
**HTTP:** `PATCH /v1/teams/{teamId}/memberships/{membershipId}` → `updateTeamMembership` · `DELETE /v1/teams/{teamId}/memberships/{membershipId}` → `deleteTeamMembership`

**Acceptance criteria**
- Given a confirmed membership, When I update roles, Then the role set is replaced. (🟢)
- Given a console team's last owner, When I try to remove them, Then deletion is prohibited. (🟢)
- Given the primary user (`team.userId`) is removed, When confirmed members remain, Then the next confirmed member is promoted. (🟢)
- Given a confirmed member is removed, When `total` is recalculated, Then it decrements. (🟡)

### US-TMS-05 — Read/replace team preferences
**As a** team member,
**I want** to get and replace team preferences,
**so that** the team can store arbitrary JSON state.
**Priority:** Should · **Unit:** Teams (RF-02) · **Confidence:** 🟢
**HTTP:** `GET /v1/teams/{teamId}/prefs` → `getTeamPreferences` · `PUT /v1/teams/{teamId}/prefs` → `updateTeamPreferences`

**Acceptance criteria**
- Given a team, When I get prefs, Then the stored JSON object is returned. (🟢)
- Given new JSON, When I replace prefs, Then the previous object is fully replaced. (🟢)

### US-ORG-01 — Create and manage team-scoped projects
**As a** team member,
**I want** to create/list/get/update/delete projects within the team context,
**so that** projects are organized and scoped to my team.
**Priority:** Must · **Unit:** Organization (RF-01..RF-05) · **Confidence:** 🟢
**HTTP:** `POST /v1/organization/projects` → `createOrganizationProject` · `GET /v1/organization/projects` → `listOrganizationProjects` · `GET/PATCH/DELETE /v1/organization/projects/{projectId}` → `getOrganizationProject` / `updateOrganizationProject` / `deleteOrganizationProject`

**Acceptance criteria**
- Given a valid team context, When I create a project, Then it is provisioned and associated with the team. (🟢)
- Given a project, When I delete it, Then asynchronous cleanup of its resources is triggered. (🟢)
- Given an invalid team, When I create, Then the init hook rejects the request. (🟢)
