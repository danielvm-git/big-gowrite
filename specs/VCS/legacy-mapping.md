## Module path
`src/Appwrite/Platform/Modules/VCS/`

## Purpose
The VCS module integrates Appwrite with external version control system providers (GitHub, GitLab, Gitea). It manages the full lifecycle of VCS installations (OAuth2 or GitHub App-based), exposes repository browsing endpoints, and receives provider webhooks that automatically trigger deployments for Functions and Sites when code is pushed or pull requests are opened.

## Workers & Tasks
None — no dedicated Workers/ or Tasks/ directories in this module. Deployment creation and cleanup are triggered inline from the webhook handlers using the shared `Deployment` trait and `deploymentsFactory` injectable.

## Key business rules
- 🟢 GitHub uses a GitHub App (App-based installation) whereas GitLab and Gitea use OAuth2 personal access tokens. The Authorize/Callback base classes handle Gitea and GitLab; GitHub has its own implementation.
- 🟢 The GitHub callback endpoint is public. To prevent an attacker from attaching their VCS tokens to an arbitrary project, the state parameter is HMAC-signed with `_APP_OPENSSL_KEY_V1` and the callback verifies the signature before proceeding.
- 🟢 Installation documents are stored in the platform database (`dbForPlatform`), scoped to a project via `projectInternalId`.
- 🟢 Webhook events are validated against a provider-specific secret (`_APP_VCS_GITHUB_WEBHOOK_SECRET`, `_APP_VCS_GITEA_WEBHOOK_SECRET`, `_APP_VCS_GITLAB_WEBHOOK_SECRET`). An invalid signature returns 403.
- 🟢 Push events authored by Appwrite's own bot email (`APP_VCS_GITHUB_EMAIL`, `APP_VCS_GITEA_EMAIL`, `APP_VCS_GITLAB_EMAIL`) are ignored to avoid deployment loops.
- 🟢 The `Deployment` trait fans out one webhook event to potentially many repositories and projects. Each repository lookup uses `providerRepositoryId` as the key.
- 🟢 Deployments are skipped when the commit message matches skip patterns (`VCS_DEPLOYMENT_SKIP_PATTERNS`), the branch does not match the configured `providerBranches` glob, or the affected files do not match `providerPaths` globs.
- 🟢 External (fork) PR deployments require explicit authorization. When not yet authorized, the system posts a comment with an authorize URL and sets a pending commit status; it does not create the deployment.
- 🟢 For site deployments, up to three preview domain rules are created in `dbForPlatform.rules`: one per unique deployment ID, one per branch, and one per commit hash prefix.
- 🟢 PR comments are protected by an optimistic lock (`vcsCommentLocks` collection, up to 9 retries with 1-second sleep) to avoid concurrent overwrites.
- 🟢 On GitHub App uninstall (`installation.deleted`), all installation documents, their linked repositories, and the `installationId`/`repositoryId` references on function and site documents are cleaned up — but only for projects whose database is in the current region.
- 🟡 The `InstallationTokens` service handles token refresh for Gitea and GitLab before each API call; GitHub App tokens are obtained differently via the VCS factory.
- 🟢 `listRepositories` and `createRepositoryDetection` use Swoole coroutines (`batch`, `go`, `WaitGroup`) for concurrent repository analysis.

## External dependencies (injected)
- `dbForPlatform` — platform-level database (installations, repositories, vcsComments, vcsCommentLocks, rules, projects)
- `getProjectDB` — factory to obtain a per-project database (functions, sites, deployments)
- `vcsFactory` — factory to build a VCS adapter (GitHub, Gitea, GitLab) from an installation or provider name
- `installationTokens` — service to refresh OAuth2 tokens for Gitea/GitLab installations
- `vcsWebhookSecret` — callable returning the configured webhook secret for a provider
- `deploymentsFactory` — factory to create deployment documents through the Deployments service
- `publisherForDeletes` — publishes delete events for installation cleanup
- `authorization` — `Utopia\Database\Validator\Authorization` for permission bypass in webhook processing
- `response`, `request`, `project`, `platform`, `user`, `redirectValidator`, `vcsConfigured`, `vcsProviders`

## Events emitted
- No Appwrite-internal events are explicitly emitted from this module (no `queueForEvents` injection). Deployments trigger downstream pipeline events via the Deployments service.
- External events posted back to provider: commit status updates (pending/success/failure), PR comments via the VCS adapter.
