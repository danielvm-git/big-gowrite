## 1. Visão geral do sistema

- **Projeto:** Appwrite (`appwrite/server-ce`) — plataforma Backend-as-a-Service self-hosted. Branch `reversa-analysis`.
- **Arquitetura:** híbrida monólito-microserviço em **PHP 8.5+ sobre Swoole 6** (runtime assíncrono), entregue como containers Docker atrás do Traefik.
- **Código:** 22 módulos de feature em `src/Appwrite/Platform/Modules/`, ~1.259 arquivos PHP de fonte, 383 arquivos de teste, **12 workers** de background (*[Revisão: era "14"; ver §5]*).
- **Framework:** ecossistema **Utopia PHP** (~40 pacotes): `utopia-php/http` (roteamento/ações), `utopia-php/database` (adaptadores multi-DB), `utopia-php/queue` (filas Redis), `utopia-php/platform` (multi-tenant), `utopia-php/auth`, `utopia-php/storage`, `utopia-php/messaging`, `utopia-php/span` (tracing).
- **Bancos:** MongoDB (primário default, replica set), MariaDB/MySQL/PostgreSQL (adaptadores via `utopia-php/database`), Redis (cache, fila, pub/sub), InfluxDB (métricas de uso).
- **Entry points:** `app/http.php`, `app/realtime.php` (websockets), `app/cli.php`, `app/worker.php`; bootstrap compartilhado em `app/init.php`.

## 2. Padrões arquiteturais

### 2.1 Estrutura de módulo
- `Module.php` — registra os serviços (Http/Workers/Tasks)
- `Services/Http.php` — registra instâncias de ações HTTP (rotas + hooks de init)
- `Services/Workers.php` / `Services/Tasks.php` — workers e tarefas CLI
- `Http/{Service}/{Action}.php` — classes de ação de endpoint (Create/Get/XList/Update/Delete ou sub-recursos de propriedade, ex. `Memberships/Status/Update.php`)

### 2.2 Padrão Action (endpoints HTTP)
- Ações estendem `Appwrite\Platform\Action` e declaram `getName()` (ex.: `createTeam`).
- `setHttpMethod()`, `setHttpPath()` (ex.: `/v1/teams`), `label('scope', ...)`, `label('event', ...)`, `param()` tipados e `inject()` de recursos; `callback()` conecta o handler.
- Scopes seguem `{resource}.{read|write}`; scopes especiais: `account`, `public`, `home`, `root`, `assistant.read`, etc.
- Hooks de init (`TYPE_INIT`) guardam grupos de rota (console-only, web-only, presença de projeto) antes de as ações rodarem.

### 2.3 Camadas de banco
- **`dbForPlatform`** — coleções de plataforma (MongoDB): `projects`, `keys`, `platforms`, `installations`, `repositories`, `rules`, `certificates`, `webhooks`, `schedules`, `reports`, `insights`, `notifications`, `devKeys`, `vcsComments`.
- **`dbForProject`** — coleções por projeto: `users`, `sessions`, `identities`, `targets`, `tokens`, `teams`, `memberships`, `buckets`, `bucket_{seq}` (arquivos), `functions`, `deployments`, `executions`, `variables`, `sites`, `migrations`, `resourceTokens`, `presenceLogs`, `databases`, `database_{seq}`, `attributes`, `indexes`, `transactions`, `transactionLogs`.
- **Data-plane** — o módulo Databases resolve um backend real por projeto via `Pool::dsn()` do pool de env-vars (MongoDB para documentsdb/legacy; PostgreSQL para vectorsdb).

### 2.4 Eventos e filas
- `queueForEvents` — barramento de eventos da plataforma; dispara webhooks, triggers de functions e realtime para labels `events.[...]`.
- Publishers (`publisherForBuilds`, `publisherForDeletes`, `publisherForMails`, `publisherForMessaging`, `publisherForDatabase`, `publisherForCertificates`, `publisherForMigrations`, `publisherForScreenshots`, `publisherForUsage`, ...) enfileiram mensagens em filas Redis consumidas por workers.
- 12 workers: builds, certificates, databases, deletes, functions, jobs, mails, messaging, migrations, notifications, screenshots, webhooks. *(stats-resources/stats-usage são publishers de evento, não workers — ver §5.)*

### 2.5 Autenticação e autorização
- Tipos de Auth: `ADMIN`, `KEY`, `SESSION`, `JWT` + `ORGANIZATION` (módulo específico).
- RBAC via autorização do Utopia + scoping por `projectInternalId` para evitar vazamento entre projetos; `authorization->skip()` em escritas privilegiadas da plataforma.
- Modelo de permissões: grupos de role (`any`, `users`, `guests`, `team:...`, `user:...`) em documentos; `fileSecurity`/bucket-level no storage.

### 2.6 Mecanismos transversais
- **Distributed locks** — uploads em chunks (storage/functions/sites), callbacks de build no Jobs worker, updates de comentários VCS (lock otimista).
- **Rate limiting** — camada de abuse do Utopia com chaves por ação (ex.: 10 desafios MFA por url+user, 15 queries do assistant por usuário).
- **Cache** — cache Redis + purga de cache de documento de projeto após escritas; cache de lista TTL para presenças.
- **Transações com lock otimista** — o módulo Databases encadeia múltiplas operações de documento e commita atomicamente com checagem de versão.

## 3. Resumos técnicos por módulo

### 3.1 Account — MFA
Autenticação multi-fator da conta (10 endpoints): enable/disable MFA, autenticadores TOTP, códigos de recuperação e desafios (TOTP/email/phone/recovery-code) com elevação de fatores de sessão.
- **Lógica-chave:** ciclo de vida TOTP (cria secret → confirma via OTP com `otphp` → persiste autenticador; autenticador verificado bloqueia recriação com 409); `factors` da sessão recalculados e deduplicados ao alternar MFA; desafios com rate-limit (10 por url+user; 10 por url+challengeId); códigos de recuperação gerados uma vez (create) e regenerados (update), armazenados com hash.
- **Entidades:** users (`mfa`), sessions (`factors`), authenticators, challenges, recovery codes.
- **Complexidade:** média.

### 3.2 Advisor — Reports/Insights
API read-mostly sobre resultados de análises automatizadas (auditorias Lighthouse, scans do database-analyzer): reports + insights aninhados, delete em cascata assíncrono.
- **Lógica-chave:** scoping por `projectInternalId`; fetch em lote de insights evita N+1; validação de cursor; `deleteReport` enfileira `DELETE_TYPE_REPORT` para limpeza assíncrona.
- **Entidades:** reports, insights. **Complexidade:** baixa.

### 3.3 Avatars
Endpoints de imagem/proxy (11, todos read-only): avatares estáticos, initials, QR, favicon, redimensionamento de imagem remota, screenshots e cartões de membro cloud.
- **Lógica-chave:** proteção SSRF (allowlist de hostnames públicos, máx. 5 redirects manuais no favicon); cor determinística de initials (5 temas, índice mod 5); screenshots via microserviço interno de browser (`_APP_BROWSER_HOST`); tier de cartão cloud (employee > hero > contributor > platinum/golden) com retry loop de refresh do token OAuth do GitHub.
- **Entidades:** nenhuma (stateless). **Complexidade:** baixa-média.

### 3.4 Compute — lib compartilhada
Infra compartilhada de Functions/Sites — Action base com helpers de deploy VCS, constantes de compute-size e validador de spec. Sem superfície HTTP.
- **Lógica-chave:** `getDefaultSpecification` (spec mais baixa/mais alta do plano); `resolveTemplateRef` com resolução de tags wildcard via GitHub; `redeployVcsFunction/Site` cria deployment + minte 3 preview rules por deploy de site.
- **Entidades:** nenhuma. **Complexidade:** baixa.

### 3.5 Console
Gateway do console e utilitários — variáveis de config, templates de e-mail, metadados de provedores OAuth2, listas de scopes, proxy do assistente de IA, redirects de URL, headers de segurança, disponibilidade de recursos.
- **Lógica-chave:** guard de console-project (Init API); web security headers (Init Web); proxy SSE do assistant para `appwrite-assistant:3003` com rate-limit 15/usuário; `getResource` checa disponibilidade de domínio (deny list, hostnames reservados, unicidade).
- **Entidades:** nenhuma (stateless). **Complexidade:** baixa.

### 3.6 Databases
Camada primária de persistência — quatro tipos de produto (`legacy` em `/v1/databases`, TablesDB, DocumentsDB, VectorsDB) + embeddings; worker de background para operações de schema assíncronas; sistema de transações com lock otimista.
- **Lógica-chave:** registries por tipo com overrides de método virtual (`getDatabaseType`, `getSDKNamespace`); schema assíncrono via `publisherForDatabase` → worker → DDL no backend → flags de status; transações encadeiam ops entre coleções, check de versão (lock otimista), commit único atômico, rollback via publisher de deletes; criptografia de atributos string (filtro encrypt); relacionamentos bidirecionais espelhados pelo worker; embeddings via `utopia-php/agents` (provider Appwrite); busca vetorial `createQuery` no VectorsDB.
- **Entidades:** databases, database_{seq}, attributes, indexes, transactions, transactionLogs. **Complexidade:** alta.

### 3.7 Functions
Compute serverless — CRUD de functions, deployments (upload/VCS/template/duplicata), variáveis, executions (sync/async/agendadas), catálogos de runtimes/specifications/templates; workers Builds/Jobs/Screenshots.
- **Lógica-chave:** upload em chunks com distributed lock; fluxo de presigned URL via serviço Deployments; execution assíncrona enfileira `FunctionMessage`; executions agendadas criam doc de schedule; JWT curto por execution (HS256) como `x-appwrite-key` para o executor; padrão join no Jobs worker (sucesso do build = callbacks exit(0)+complete(+manifest) deduplicados por CloudEvent id); truncamento de logs; retenção de executions.
- **Entidades:** functions, deployments, executions, variables. **Complexidade:** alta.

### 3.8 Health
Diagnósticos de admin (25 endpoints) — probes de HTTP, pools de DB, cache, pub/sub, NTP, certificados SSL, antivírus, geo, dispositivos de storage e tamanhos de fila.
- **Lógica-chave:** threshold de fila (default 5000) → `HEALTH_QUEUE_SIZE_EXCEEDED`; `/health/time` UDP raw para `time.google.com:123` com drift ±60s; checagem de expiração de certificado; `/health/anti-virus` e `/health/geo` respeitam flags de env.
- **Entidades:** nenhuma. **Complexidade:** baixa.

### 3.9 Migrations
Importação de dados de admin entre provedores (Appwrite, Firebase, Supabase, NHost) e export/import de coleções CSV/JSON.
- **Lógica-chave:** máquina de estados pending → processing → completed/failed (retry apenas quando failed); endpoints de relatório de provedor conectam ao vivo no momento do request; validação de service-account Firebase; credenciais Supabase/NHost persistidas no doc; política `onDuplicate` (fail/skip/overwrite); export CSV/JSON grava no bucket interno da plataforma + notificação por e-mail opcional; decrypt/decompress do arquivo de origem.
- **Entidades:** migrations. **Complexidade:** média.

### 3.10 Notifications
Notificações in-app do console + pixel de open-tracking de e-mail.
- **Lógica-chave:** guard console-only; filtros por channel/resourceType/resourceId; pixel decodifica JWT assinado (HS256, `_APP_NOTIFICATIONS_TRACKING_SECRET`), seta `read=true`/`firstSeen`/`lastSeen`; erros silenciados.
- **Entidades:** notifications. **Complexidade:** baixa.

### 3.11 Organization
Gestão de projetos com escopo de time sob `/v1/organization/projects`.
- **Lógica-chave:** gate por time (Init valida `$team`); provisionamento de projeto (filtro de região, pool de DSN, tabelas compartilhadas vs namespace do projeto, bootstrap de coleções); ownership verificado via `teamInternalId`; delete enfileira limpeza; hook `afterProjectCreation`.
- **Entidades:** projects. **Complexidade:** média.

### 3.12 Presences
Estado de presença em tempo real por projeto (`presenceLogs`).
- **Lógica-chave:** semântica de upsert; expiry **default de 15min** no upsert quando `expiresAt` não é fornecido (🟢 `Presences/HTTP/Upsert.php:166` → `$expiresAt ?? DateTime::addSeconds(new \DateTime(), 15 * 60)`), **máximo +30 dias** validado como data futura no update (🟢 `Presences/HTTP/Update.php:100-104`, `DatetimeValidator`); soft-expire na leitura; cache de lista TTL (0–86400s) com header `X-Appwrite-Cache`; flag de purge invalida; escrita de `userId` restrita a chamadores key/privilegiados. *[Revisão: claim de 15min/30d verificado e CONFIRMADO no código.]*
- **Entidades:** presenceLogs. **Complexidade:** baixa.

### 3.13 Project
Configuração e ciclo de vida de projeto único — keys (padrão + JWT efêmeros), variáveis, plataformas, OAuth2, SMTP, templates, políticas de security/auth, métodos de auth, serviços, protocolos, labels.
- **Lógica-chave:** keys efêmeras são JWT HS256 não persistidas; keys padrão persistidas com scopes/expiry; update de SMTP testa conexão real; templates editáveis apenas com SMTP custom habilitado; credenciais OAuth2 no map do doc do projeto, secrets retornados vazios, `verifyCredentials` no enable; escrita de variáveis marca functions/sites `live=false` (rebuild).
- **Entidades:** keys, platforms, variables (project-scoped). **Complexidade:** alta.

### 3.14 Projects
Ciclo de vida de projeto em nível de plataforma — criação (provisionamento de DB), metadados, transferência de time, dev keys tombstoned, schedules CRON, estágios de onboarding.
- **Lógica-chave:** seleção de DSN na criação (filtro de região/aleatório/override); tabelas compartilhadas vs dedicadas; dev keys tombstoned (`DEV_KEY_GONE`); schedules validados contra o DB do projeto; pulo de estágio rastreado por ator; transferência de time propaga permissões para installations/repositories/comentários VCS.
- **Entidades:** projects, devKeys, schedules. **Complexidade:** média.

### 3.15 Proxy
Rotas de domínio customizado (API/function/site/redirect) com verificação de DNS + provisionamento de TLS.
- **Lógica-chave:** id da rule = `md5(domain)` no modo legado; domínios de propriedade da Appwrite auto-verificados; gate CAA antes da emissão; alvos CNAME diferem por tipo de recurso; ciclo de status created → unverified → verified → certificate_generating; retry via `updateRuleVerification`; limpeza de regras órfãs em conflito; delete em cascata com limpeza de certificado.
- **Entidades:** rules, certificates. **Complexidade:** média.

### 3.16 Sites
Hospedagem de sites estáticos/SSR — CRUD, deployments (upload/template/VCS/duplicata), ativação, cancelamento de build, variáveis, catálogos de framework/template/spec.
- **Lógica-chave:** upload em chunks com lock de 600s; `LockContention` → 429 com `Retry-After`; todo deployment minte uma preview rule (`verified`) sob `sitesDomain`; ativação exige deployment ready; cancelamento bloqueado quando ready/failed; delete reseta `latestDeploymentId`; variáveis setam `live=false`.
- **Entidades:** sites, deployments, variables. **Complexidade:** alta.

### 3.17 Storage
Storage de objetos — buckets + arquivos com security, compressão, criptografia, antivírus, transformações de imagem; download/view/preview/push.
- **Lógica-chave:** criação de bucket provisiona `bucket_{seq}` a partir do schema de config; upload em chunks (`Content-Range`) com distributed lock; GZIP/ZSTD + AES-128-GCM no finalize quando `sizeOriginal ≤ buffer`; scan ClamAV; `fileSecurity` vs permissões de bucket; expansão de grupos de role; previews via Imagick; endpoint push com JWT (HS256, 1h); download/view com suporte a HTTP Range.
- **Entidades:** buckets, files. **Complexidade:** alta.

### 3.18 Teams
Colaboração — teams, memberships, preferências, fluxo de invite/confirm.
- **Lógica-chave:** invite via email/SMS/userId; add direto em modo privilegiado; criação de usuário stub quando não há match; confirm valida invite secret (`proofForToken`) e cria sessão para convidado não logado; `membershipsPrivacy` controla exposição de campos; proteção de último owner do console; promoção de usuário primário; delete em cascata (sync de memberships, async de projetos do time).
- **Entidades:** teams, memberships, users. **Complexidade:** média.

### 3.19 Tokens
Tokens de recurso de curta duração para acesso público por URL a arquivos do storage.
- **Lógica-chave:** secret aleatório de 128 bytes armazenado criptografado; `resourceId` composto `bucketId:fileId`; criação exige permissão UPDATE no bucket/file; expiry opcional futuro; ADMIN/KEY apenas; escritas com rate-limit.
- **Entidades:** resourceTokens. **Complexidade:** baixa.

### 3.20 Users
Gestão de usuários por admin — CRUD, imports de hash (Bcrypt/MD5/Argon2/SHA/PHPass/Scrypt/Scrypt-Modified), todos os sub-recursos (sessions, targets, tokens, memberships, identities, prefs, labels, status, MFA).
- **Lógica-chave:** unicidade de email entre users+identities; `personalDataCheck`; gates de política de e-mail (disposable/canonical/free/corporate); sessions criadas por admin pulam verificação de senha (`SESSION_PROVIDER_SERVER`); JWT assinado HS256; delete hard-deleta identities/targets e enfileira limpeza no worker; otimizações de list (fetch em lote de targets, skipFilters).
- **Entidades:** users, sessions, identities, targets, tokens, authenticators, challenges. **Complexidade:** alta.

### 3.21 VCS
Integração com provedores VCS (GitHub App, OAuth2 GitLab/Gitea) — installations, navegação de repositórios, deployments dirigidos por webhook.
- **Lógica-chave:** state assinado com HMAC no callback; validação de assinatura de webhook (403 em mismatch); eventos de push de bot-email ignorados; padrões de skip/glob filtram deploys; trait de deployment faz fan-out para vários repos/projects; deploys de site minteiam 3 preview rules; deploys de fork externo exigem autorização explícita; comentários com lock otimista; corrotinas Swoole para análise concorrente de repos.
- **Entidades:** installations, repositories, vcsComments, vcsCommentLocks. **Complexidade:** alta.

### 3.22 Webhooks
CRUD de webhooks de projeto + rotação de secret; projeto console bloqueado.
- **Lógica-chave:** secret auto de 128 hex; `signatureKey` removido nas leituras, retornado apenas no create/rotação; scoping por `projectInternalId`; re-enable reseta `attempts`; mapeamentos de campos `httpUser`/`httpPass`/`security`; aliases de path legados.
- **Entidades:** webhooks. **Complexidade:** baixa.

## 4. Algoritmos e lógicas-chave (transversais)

1. **Ciclo de vida TOTP/MFA** (Account) — geração de secret, confirmação via OTP, elevação de `factors` na sessão, rate-limits por desafio.
2. **Upload multipart em chunks** (Storage/Functions/Sites) — `Content-Range`, distributed lock por recurso, finalize com compressão/criptografia/antivírus.
3. **Sistema de transações com lock otimista** (Databases) — staging de ops multi-coleção, cheque de versão, commit atômico, rollback via publisher.
4. **Fan-out de deploy VCS** (VCS/Compute) — webhook → trait de deployment → vários repos/projects; preview rules por deploy de site.
5. **Verificação de domínio e TLS** (Proxy) — gate CAA, alvos CNAME por tipo, máquina de status com retry e limpeza de órfãos.
6. **Padrão join no Jobs worker** (Functions/Sites) — callbacks de build deduplicados por CloudEvent id, sync via `waitForPendingJob`.
7. **Imports de hash de senha** (Users) — Bcrypt, MD5, Argon2, SHA, PHPass, Scrypt, Scrypt-Modified; upsert com `force`/`userId`.
8. **Presença com TTL cache** (Presences) — upsert, soft-expire, cache de lista TTL + header de cache.
9. **Open-tracking pixel** (Notifications) — JWT HS256 assinado, erros silenciados, atualização de leitura.
10. **SSRF protection** (Avatars) — allowlist de hostnames, redirects limitados, proxy interno de browser.
