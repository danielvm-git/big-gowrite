## Module path
`src/Appwrite/Platform/Modules/Databases/`

## Purpose
The Databases module is Appwrite's primary data persistence layer, exposing a multi-paradigm database API to developers. It manages four distinct database product types — **legacy** (the original `/v1/databases` collection-document API), **TablesDB** (`/v1/tablesdb`, a SQL-oriented tables/rows/columns API), **DocumentsDB** (`/v1/documentsdb`, a NoSQL document store), and **VectorsDB** (`/v1/vectorsdb`, a vector/embedding-native database). Each product type shares the same underlying PHP class hierarchy through inheritance, with type-specific behaviour gated on virtual method overrides (e.g. `getDatabaseType()`, `getSDKNamespace()`). The module also provides an **Embeddings** endpoint (`/v1/embeddings/text`) for generating vector embeddings from text. A background **Databases worker** processes asynchronous schema operations (create/delete attribute, create/delete index), propagating them to the actual backend database and updating status flags. A cross-cutting **transaction system** provides optimistic-locking ACID-like semantics for staging multiple document operations across collections before a single atomic commit.

### TablesDB API (`/v1/tablesdb`)
Mirror of the legacy API with:
- Databases → Databases (`/v1/tablesdb`)
- Collections → Tables (`/v1/tablesdb/:databaseId/tables`)
- Attributes → Columns (`/v1/tablesdb/:databaseId/tables/:tableId/columns`)
- Documents → Rows (`/v1/tablesdb/:databaseId/tables/:tableId/rows`)
- Transactions at `/v1/tablesdb/transactions`
- SDK namespace: `tablesDB`

### DocumentsDB API (`/v1/documentsdb`)
Same as TablesDB but without column-type-specific endpoints (no `attributes/{type}` tree).
- SDK namespace: `documentsDB`

### VectorsDB API (`/v1/vectorsdb`)
Same as legacy collections/documents but with an extra endpoint:

| Method | Path | Action ID | Scope | Description |
|--------|------|-----------|-------|-------------|
| POST | `/v1/vectorsdb/:databaseId/collections/:collectionId/documents/query` | `createVectorsDBDocumentsQuery` | `documents.read` | Vector similarity search (POST version of list) with optional TTL cache |

SDK namespace: `vectorsDB`

|--------|------|-----------|-------|-------------|
| POST | `/v1/embeddings/text` | `createTextEmbeddings` | `documents.write` | Generate vector embeddings from a batch of text strings |

## Workers & Tasks

| Name | Trigger | Purpose |
|------|---------|---------|
| `databases` | Queue message (`DatabaseMessage`) | Processes asynchronous schema operations: `DATABASE_TYPE_DELETE_DATABASE`, `DATABASE_TYPE_DELETE_COLLECTION`, `DATABASE_TYPE_CREATE_ATTRIBUTE`, `DATABASE_TYPE_DELETE_ATTRIBUTE`, `DATABASE_TYPE_CREATE_INDEX`, `DATABASE_TYPE_DELETE_INDEX`. Updates attribute/index status to `available`, `failed`, or `stuck`. Purges cached collection and document entries after each operation. Sends realtime events on completion. |

## Key business rules

- 🟢 **Database types are distinct products** — each of legacy, tablesdb, documentsdb, and vectorsdb has its own URL path prefix, SDK namespace, and terminology (collection vs. table, document vs. row, attribute vs. column). The action PHP classes are reused via inheritance and `getDatabaseType()` override.
- 🟢 **Attribute and index creation is asynchronous** — the HTTP action creates a metadata document with `status: 'processing'` and enqueues a `DatabaseMessage`. The background `Databases` worker performs the actual DDL against the backing store and flips the status to `available` or `failed`.
- 🟢 **Collection create resolves the data-plane DSN before writing metadata** — if provisioning fails (e.g. no dedicated-db DSN), no orphaned metadata row is left behind.
- 🟢 **Inline attributes and indexes on `createCollection`** — callers may pass `attributes[]` and `indexes[]` arrays; relationship attributes are explicitly rejected from this inline path.
- 🟢 **Bulk operations are API-key/admin only** — the regular session-user path for create/update/delete only allows single-document operations.
- 🟢 **Transaction staging** — any write endpoint accepts an optional `transactionId`; when set, the operation is staged into `transactionLogs` and an immediate mock response is returned. The real writes happen only on `PATCH /transactions/:id` with `commit=true`.
- 🟢 **Transaction optimistic concurrency** — during commit, `handleBulkUpdateOperation` compares `$updatedAt` of each document in the transaction log against the timestamp of the staged operation and throws `ConflictException` on conflict.
- 🟢 **Permission aggregation** — `Permission::aggregate()` resolves short-hand roles (e.g. `any`) into their constituent permission strings before persisting.
- 🟢 **Document security** — collections may enable `documentSecurity`, giving individual documents their own read/write permission sets in addition to (or instead of) collection-level permissions.
- 🟢 **String attribute encryption** — string attributes may be created with `encrypt=true`; the server stores an `encrypt` filter and the attribute cannot be queried. Requires minimum size of `APP_DATABASE_ENCRYPT_SIZE_MIN` and a paid plan (`databasesAllowEncrypt`).
- 🟢 **Relationship attributes use a separate creation path** — two-way relationships create a mirrored attribute on the related collection via the background worker; the twoWayKey attribute is also updated to `available` after creation.
- 🟢 **Index limits per collection** — `createIndex` checks the count of existing indexes against the adapter-reported `getLimitForIndexes()` (≤60 checked with count up to 61).
- 🟡 **VectorsDB has a PostgreSQL backend** — `Pool::dsn()` defaults to `postgresql` scheme for vectorsdb type; documentsdb defaults to `mongodb`.
- 🟡 **Attribute deletion cascades to indexes** — the Databases worker removes or trims any index that referenced the deleted attribute.
- 🟡 **Database deletion is recursive** — the worker iterates and deletes every collection (via `deleteByGroup`) before dropping the per-database metadata collection.
