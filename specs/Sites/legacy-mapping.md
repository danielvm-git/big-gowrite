## Module path
`src/Appwrite/Platform/Modules/Sites/`

## Purpose
The Sites module manages the full lifecycle of static and server-side-rendered (SSR) web sites hosted on Appwrite. It handles site creation and configuration (framework, build/runtime specs, VCS connection), deployment creation via file upload, public GitHub template, VCS branch/commit, or duplication of an existing build, deployment activation (switching the live deployment), build cancellation, variable management (scoped build and runtime environment variables), and catalogue endpoints for supported frameworks, site templates, and compute specifications.

## Key business rules
- 🟢 When creating a site with a VCS provider repository, both `installationId` and `providerBranch` are required; omitting either throws `GENERAL_ARGUMENT_INVALID`.
- 🟢 The `adapter` field (static / ssr) is validated against the chosen `framework`'s allowed adapters; passing an unsupported adapter throws `GENERAL_ARGUMENT_INVALID`.
- 🟢 When a VCS repository is connected, a `repositories` document is created in `dbForPlatform` and a webhook is ensured on the provider. If webhook creation fails, the orphaned repository document is deleted.
- 🟢 On `updateSite`, omitting `providerRepositoryId` (null) on an already-connected site preserves existing VCS settings. Passing an empty string explicitly disconnects VCS and deletes all `repositories` documents for that site.
- 🟢 `updateSite` sets `live=false` when name, buildCommand, installCommand, startCommand, outputDirectory, providerRootDirectory, or framework changes — signalling the site needs a redeploy to go live.
- 🟢 Deployment uploads are chunked and protected by a per-project per-site per-deployment distributed lock (600 s timeout). A `LockContention` exception returns HTTP 429 with `Retry-After: 5`.
- 🟢 Each new deployment (upload, template, VCS, duplicate) creates a preview `rules` document in `dbForPlatform` with a unique subdomain under `platform['sitesDomain']`, immediately with `status=verified`.
- 🟢 `updateSiteDeployment` (activate) requires the deployment status to be `ready`; non-ready deployments throw `BUILD_NOT_READY`.
- 🟢 Deployment cancellation (`updateDeploymentStatus`) is blocked for deployments already in `ready` or `failed` state (throws `BUILD_ALREADY_COMPLETED`). The cancel is written under the jobs-worker's per-deployment lock to avoid log-line races.
- 🟢 Deleting a deployment resets `latestDeploymentId` on the site to the next most-recent deployment, and clears `deploymentId` if the deleted deployment was the active one.
- 🟢 Secret variables (`secret=true`) cannot be downgraded to non-secret; attempting throws `VARIABLE_CANNOT_UNSET_SECRET`.
- 🟢 Creating or updating a variable sets `site.live=false`.
- 🟢 `getDeploymentDownload` accepts either a session/API-key (privileged caller) or a presigned deployment token (`Token::verify`); unauthenticated callers without a valid token are rejected with `USER_UNAUTHORIZED`.
- 🟢 `listFrameworks` filters the framework list by `_APP_SITES_RUNTIMES` allowlist and drops frameworks that have no enabled build runtimes.
- 🟢 `listSpecifications` filters by plan `runtimeSpecifications`/`buildSpecifications` and by `_APP_COMPUTE_CPUS`/`_APP_COMPUTE_MEMORY` env caps.
- 🟡 The `_APP_RULES_FORMAT=md5` env var triggers legacy MD5-based rule ID generation (the comment notes removal after 1.7.x migration).
