## Purpose
The Migrations module lets admin users import project data from external BaaS providers (Appwrite, Firebase, Supabase, NHost) and move data between formats (CSV, JSON) or between Appwrite instances. Each migration attempt is persisted as a `migrations` document that transitions through status states (`pending` → `processing` → `completed`/`failed`). A "report" endpoint is available for each provider to preview what would be migrated before committing. Failed migrations can be retried. The module also supports collection-level CSV and JSON export/import, allowing schemaless and SQL-backed database types.

## Workers & Tasks
None are registered in this module's `Module.php`. The actual migration processing is handled by a separate migration worker (triggered via `publisherForMigrations`). The worker is expected to be registered elsewhere (e.g. `bin/worker-migrations`).

## Key business rules
- 🟢 All migration creation endpoints are admin-only (`AuthType::ADMIN`).
- 🟢 Migration documents are created in a `pending` state, then `publisherForMigrations` enqueues the actual processing.
- 🟢 Retrying (`Update.php`) only works when `status === 'failed'`; any other status throws `MIGRATION_IN_PROGRESS`.
- 🟢 Firebase migration validates the service account JSON for `project_id`, `client_email`, and `private_key` fields before creating the document.
- 🟢 Supabase and NHost migrations store database credentials (host, username, password) in the `credentials` field of the migration document.
- 🟢 Appwrite-to-Appwrite migrations support an `onDuplicate` policy: `fail` (default), `skip`, or `overwrite`.
- 🟢 Report endpoints connect directly to the source provider at request time; connection failures surface as `MIGRATION_PROVIDER_ERROR`.
- 🟢 CSV/JSON export always writes to an internal platform bucket (`default`); the `notify` flag sends an email to the initiating user on completion.
- 🟢 CSV/JSON import decrypts and decompresses the source file before copying to `deviceForMigrations` when the file has encryption or compression applied.
- 🟢 CSV export supports configurable `delimiter`, `enclosure`, `escape`, and `header` options.
- 🟢 Database type validation restricts CSV imports/exports to `CSV_ALLOWED_DATABASE_TYPES`; all database types are supported for JSON.
- 🟢 Import/export operations build the `resources` array from `Transfer::extractServices()` based on the database type group.
- 🟡 The CSV import endpoint also registers an HTTP alias at `/v1/migrations/csv` for backward compatibility.
- 🟢 `resourceType` label value is not declared on this module (migrations are a cross-cutting concern without a RESOURCE_TYPE_ constant).
